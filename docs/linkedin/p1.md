# LinkedIn — Project 1 post (draft)

---

**A retailer wants daily KPIs — what's selling, are deliveries on time, do customers come back — without paying for a data warehouse.**

Project 1 of my 7-day Data Engineer portfolio is live: a batch **retail analytics warehouse on AWS**, built on the public Olist Brazilian e-commerce dataset (~100k orders, 2016–2018).

**Architecture:** `ingest.py` lands the 9 source tables as partitioned Parquet in S3 → Glue Data Catalog → **Athena** (pay-per-query, nothing running) → **dbt** (9 staging views → 4 marts: orders, customers, delivery performance, retention cohorts) → a **Streamlit** dashboard. **Dagster** runs the whole thing on a daily schedule. **Terraform** owns the infra.

**Three decisions worth explaining:**

- **Athena instead of a warehouse.** The question is small and read-only. Pay-per-query over Parquet costs pennies and there's no cluster to leave running. `terraform destroy` at the end of every session; a $5 budget alarm as a backstop.
- **A ~2 MB data slice is committed to the repo.** CI runs the *entire* dbt graph on it via DuckDB, with no cloud credentials, on every push. Two thin cross-database macros let the same models run on Athena (Trino) and DuckDB.
- **Bronze stays untyped (all strings); dbt casts once, explicitly, in staging.** Parquet written by pandas has unpredictable types — better to make the cast a visible, tested transformation.

**What the data says:** retention is *effectively zero* — of 96k customers, only **3% ever order twice**. And delivery ETAs are padded hard: 93% of orders are "on time," but the average order arrives **~11 days before** the promised date. The customer-facing estimate is roughly 2× the real transit time.
